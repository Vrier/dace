# DACE — working notes for Claude Code / Cowork

DACE (*Dictionary of Alternations in Clause Embedding*) is Thomas Stephen's online resource mapping the alternation patterns of English clause-embedding predicates. This repo builds a **static site**: the Explorer at https://dace.tstephen.com and the unlisted Judge (annotation tool) at `/judge/`. It began as a Claude Design handoff (30 Sept 2026); `notes/handoff-migration.md` records what changed in the move to production.

Pushing to `main` deploys: GitHub Actions runs `npm test` and, if green, moves branch `live` to that commit; a cron job on the VPS pulls `live` every two minutes into the clone Caddy serves (`/srv/dace/site`). Never push to `live` yourself. See `DEPLOY.md`.

## Layout

| Path | What it is |
|---|---|
| `data/predicates.csv` | **Source of truth.** One row per predicate: classes, 26 binary features (0/1, 5 = marginal), factivity, veridicality, notes. |
| `data/ahg_senses.csv` | Every AHG sense of the multi-sense predicates (the CSV holds only the primary sense + alt class names). |
| `data/frames.lock.json` | Version + hash of every test-sentence template (frame *item* `<feature>:<table>`). Updated only by `npm run frames:lock`; baked into `data.js` as `DACE_FRAME_VERSIONS`. |
| `data/cells.csv` | **Generated** by `npm run consolidate`, committed: where each cell's value came from (`verb,feature,value,status,n,agreement,frame_v`; status consensus / provisional / contested / adjudicated / estimated / coded / lexical / na). Baked into `data.js` (a status letter per column, `p.st`; judges and agreement, `p.jn`) and published at `/data/cells.csv`. `npm test` checks it agrees with `predicates.csv`. |
| `data/adjudications.csv` | Thomas's decisions on contested (or any judged) cells: `verb,feature,value,rationale,date`. Hand-edited; always wins over the judges. |
| `data/consolidation.json` | Consolidation thresholds: `min_judges`, `majority`, `current_frames_only`, `use_legacy`, `min_gold_accuracy`, `min_gold_seen`, `author` (judge codes), `exclude_author`. |
| `data/gold.csv` | Gold cells for the Judge (`verb,feature,expected`; expected = acceptable / marginal / unacceptable): uncontroversial cells spread through every judge's queue as attention checks. Baked into `data.js` as `DACE_GOLD`; `npm test` validates it. Empty until Thomas picks them. |
| `data/annotations/` | Committed sidecar files (example sentences, derived nominals), baked into the build. The Judge's per-judge files come from the server (see *The Judge* below). |
| `data/concordance.csv`, `data/sources.js` | Literature-inventory concordance and source registry for the planned Coverage tab (not loaded by the site yet). |
| `src/` | The two apps. `*.jsx` = React components; plain `*.js` = data/lexicon modules shared by both apps; `explorer.*`/`judge.*` = page templates + CSS; `judge-sync.js` = the Judge's account/server layer. |
| `docs-src/` | Markdown for the Alternations, Verb Classes and About documents (`_page.html` = standalone page template). |
| `provenance/` | Gitignored. Third-party datasets kept locally for reference (MegaAttitude); the build reads nothing from here since Oct 2026. |
| `scripts/` | `build.mjs`, `check.mjs` (= `npm test`), `serve.mjs`, `frames-lock.mjs` (= `npm run frames:lock`), `consolidate.mjs` (= `npm run consolidate`), and `lib/` (`consolidate.mjs` holds the rules, `agreement.mjs` Krippendorff's α). |
| `site/` | **Generated** by `npm run build` and committed. Never edit by hand. |
| `notes/` | Audit, methodology, coverage report, AHG reconciliation, handoff migration record. |
| `uploads/` | Copyrighted reference material (e.g. the AHG paper text). Gitignored — never commit. |

## Golden rules

1. Never edit `site/`. Change `src/`, `data/` or `docs-src/`, run `npm run build`, run `npm test`, commit sources **and** `site/` together. CI fails the deploy if `site/` is stale.
2. Don't add derived fields to the CSV. The build computes `display`, `lemma` (adjectival `be_*` rows query Wiktionary by the adjective), `levin_class` (from `src/levin_classes.js`), the per-sense `ahg` list and `notesClean`.
3. DACE ships no third-party data (MegaVeridicality scores were removed in Oct 2026 to keep licensing simple). `factivity` and `veridicality` in the CSV are DACE's own coding.
4. Heading text in `docs-src/alternations.md` and `verb_classes.md` *is* the anchor (`## 27. Copular *be* …` → `#27-copular-be-adjectivenoun-constructions`). `src/glossary.js`, `levin_classes.js` and `ahg.js` deep-link to them; `npm test` fails if a heading rename breaks a link — update the URL there too.
5. The `src/*.jsx` files are compiled to classic scripts that share **one global scope** (as in the prototype): exports go through `Object.assign(window, …)`, and a top-level name may be declared in only one file (`engine.jsx` owns `useState` etc.; others alias, e.g. `uS`, `useStateD`; `judge-sync.js` declares nothing but `window.DACE_SYNC`). `npm test` catches clashes.
6. Never commit `uploads/` or `.deploy-key*`.

## Common tasks

- **Bring in judgements from the Judge.** From the Judge's *Judges* panel (`dace_admin` accounts only) download *All events* (`events.csv`) and the *Judge register* (`judges.csv`) into `judgements/` (gitignored — raw judgements are not published). `events.csv` is the append-only log: `event_id,judge,verb,feature,kind,response,item,frame_v,sentence,gold,repeat,at`, judges by code (J01 …), never email; responses are raw sentence judgements (acceptable / marginal / unacceptable / cant_judge, or `clear`). Then `npm run consolidate` (add `-- --dry-run` to preview): it prints each judge's gold accuracy and retest agreement, ordinal Krippendorff's α and pairwise agreement, rewrites only the feature cells of `data/predicates.csv` that the judges have decided, regenerates `data/cells.csv`, and lists split cells in `judgements/contested.md`. Decide those in `data/adjudications.csv`, run it again, then `npm run build`, `npm test` and commit `data/` and `site/`. The rules (consensus = at least `min_judges` judges and `majority` agreeing; provisional = fewer, all agreeing; contested keeps the old value) are in `scripts/lib/consolidate.mjs`; `npm test` runs them on a fixture. Never edit a judged cell of `predicates.csv` by hand — add an adjudication instead.
- **Publish custom example sentences / nominals.** Download a judge's `annotations.json` (Judges panel) or their own exports → save the `sentences` / `nominals` objects as `data/annotations/sentences.json` / `nominals.json` → rebuild.
- **Judge frames.** Test sentences are built by `src/frames.js` from per-class templates in the **past tense** (`[VD]`; the present forces habitual readings on eventive verbs), with `[VN]` for passives, irregular forms in `DACE_IRREGULAR`, consonant doubling in `daceDouble`. The that-omission test drops the "(that)" in the Judge only. Predicates that need a direct object before their clause (*fool*, *inform*, *mislead* …: `DACE_OBJECT_REQUIRED` in `src/frames.js`, chosen by hand) take the tell table's frames whatever their class, so the object is present in every frame that isn't testing it (`daceFrameType`). Both the Judge's rendering and the plain sentence that will be logged with a judgement come from `daceTestSentence(…, { judge: true })` (`daceTestItem` adds the item id and version), so they cannot drift apart. **Every template is versioned:** after changing one, run `npm run frames:lock` (bumps that item's version in `data/frames.lock.json`), then `npm run build`; `npm test` fails until you do. Never edit the lock file by hand or reuse a version — judgements are tied to item + version (PLAN.md, *Judgement data*). Under each question the Judge shows a minimal pair from `DACE_FEATURE_PAIRS` (`src/glossary.js`, one clearly good and one clearly bad predicate — edit freely); the derived-nominal question lists `DACE_NOMINAL_SUFFIXES` and is a plain Yes / No (logged as acceptable / unacceptable), followed after Yes by boxes for the noun(s); its frame shows the nominal as a blank, never DACE's own candidate. Question types (`QTYPE` in `judge-app.jsx`): `derived_nominal` is Yes / No plus the noun(s), `neg_raising` is a meaning question ("can the first mean the second?", Yes / No / Can't tell; its frames are two sentences joined by ` ≈ `); both log acceptable / unacceptable / cant_judge, so nothing downstream changes. Every other feature: Judgement buttons: Acceptable (1) / Unacceptable (0) / Marginal (5) / Can't judge (9) judge the *sentence*, and the response is stored as given; for `weak_island` and `stative` (`DACE_INVERTED`) an acceptable sentence means the feature is absent, which the card explains and consolidation applies — the Judge never stores feature values. The card doesn't show the cell's current CSV value (it would anchor the judge).
- **Features the Judge never shows.** `phrasal` and `be_copula` are lexical facts set in the CSV (`DACE_UNJUDGED` in `src/frames.js`), so the judgeable grid is 946 × 24 minus the copular n/a cells = 22,400.
- **Copular predicates (`be_*`).** The factive passive and the ditransitive are verbal constructions, so those cells are fixed at 0 (`npm test` enforces it), skipped by the Judge and shown as n/a in the Explorer — the list is `DACE_COPULAR_NA` in `src/frames.js`, which also holds the copular versions of the auxiliary-based frames (`DACE_FRAMES.copular`, `[ADJ]` = the bare adjective).
- **Add a predicate.** Add a row to `data/predicates.csv` (lower-case key, underscores for spaces, `be_` prefix for adjectival predicates). If it belongs to a Levin-style class, add it to that class's `members` in `src/levin_classes.js` and the list in `docs-src/verb_classes.md`. If it has several AHG senses, list all of them in `data/ahg_senses.csv`.
- **Edit documentation.** Edit `docs-src/*.md`; the build makes both the standalone pages (`site/docs/*.html`) and the Explorer's side-panel fragments. `about.md` takes `{{placeholders}}` filled from the data (`predicates`, `estimated`, `version`, …).
- **Change the interface.** Edit `src/*.jsx` / `src/explorer.css`, rebuild, check with `npm run serve`. The look is the handoff's "Reading Room" direction; readers can switch theme and row density in Settings.
- **Make someone a judge.** Judges register on the Judge's own Register tab with a *judge code*. Codes live in COMPOSE's PocketBase: admin dashboard (compose.tstephen.com/_/) → `invite_codes` → new record with `judge` ticked (`max_uses` 0 = unlimited). To let an account see every judge's progress and download their files, tick `dace_admin` on its `users` record. An existing COMPOSE account becomes a judge by ticking `judge` on it.
- **Release.** Bump `version` in `package.json` (shown on the About page and in the citation), rebuild, commit, push.

## The Judge

`/judge/` is behind a login. Judges sign in against **COMPOSE's PocketBase** (`https://compose.tstephen.com`; code in `Vrier/compose`, `server/pb_hooks/dace.pb.js` + `dace_lib.js`, migrations `1751700008` and `1751700009`), using the SDK copied into `site/assets/pocketbase.js` by the build. Anonymous visitors see only the sign-in card; accounts without `judge` see a "not a judge" card. The page stays unlisted (robots.txt, `noindex`).

- **Storage.** Every act of judging is **appended** to `dace_events` (kinds `judge`, `flag`, `unflag`, `note`, `sentence`, `nominal`; a `judge` event carries the response, the frame `item` and `frame_v`, and the exact `sentence` shown, from `daceTestItem`). Events are never edited or deleted; the server stamps `at`. The server keeps one `dace_judgements` record per (judge, predicate) as a cache of the judge's current state — `{ v: 2, r: {feature: response}, flags, t: {feature: ISO time}, notes, sentence, nominal }` — which the Judge only reads. `src/judge-sync.js` loads that cache on sign-in, applies each change locally at once and sends the events in order (queued, retried with backoff; the header shows *saved* / *saving…* / *n unsaved — retrying*, or *n refused* if the server rejected an event as invalid) and keeps nothing in localStorage but the SDK's token.
- **Judges.** Each judge has a code (J01, J02 … assigned by the server) and answers a three-question profile on first sign-in (variety of English, linguist or not, consent to publish their pseudonymised judgements); *Your profile* in the menu edits it.
- **Gold and retest.** In random order the gold cells (`data/gold.csv`) are moved forward, one every 25 items (`GOLD_EVERY`), and their events are marked `gold`. After about one judgement in 100 (`RETEST_EVERY`) the Judge shows a *check item*: a cell this judge answered at least a day ago, without their earlier answer; that event is marked `repeat` and never changes the cache.
- **Order.** By default each judge works through the 24,596 cells in a random order seeded by their account id (`judgeOrder` in `judge-app.jsx`), so it is stable across devices; the header's order menu (or the phone Menu) switches to CSV order (predicate by predicate, feature by feature) and back, keeping the current item. The choice is a browser preference, not data. `‹ ›` move through the chosen order, `U` skips to the next unjudged cell, the coverage map jumps anywhere.
- **Phone layout.** Below 700px (`useNarrow` in `judge-app.jsx`, `@media (max-width:700px)` in `judge.css`): one-row header with a single Menu (coverage map, exports, Judges, sign out) and a dot for save status, the four judgement buttons in a 2×2 grid, and a bottom bar (Back · position · Unjudged · Next) instead of the side arrows and keyboard footer.
- **Local testing.** Run a throwaway PocketBase from the COMPOSE repo (`cd server && ./pocketbase serve --http 127.0.0.1:8123 --dir /tmp/pbdata --hooksDir ./pb_hooks --migrationsDir ./pb_migrations --publicDir ./pb_public`), create a superuser and a judge invite code, then open `http://localhost:8000/judge/?pb=http://127.0.0.1:8123`.
